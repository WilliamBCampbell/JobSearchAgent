# Employer form preparation and sending

The coordinator now continues from a qualifying role's package into employer form inspection. Inspection uses public GET requests and sends no candidate answers or files. Lever HTML and Greenhouse public question definitions become typed field contracts. Other portals produce a saved normal-browser handoff.

The plan preserves question text, required flags, option values, implicit privacy notices, the final button label, and the requisition route. Stable contact fields use existing confirmed memory. Custom question keys include their field name, wording, and options. Answers default to this application; the user can explicitly choose Global for reusable factual answers. Salary, travel, consents, and other role-specific commitments remain local. [Answer scope controls](INTERVENTIONS.md) describe reuse and corrections. Unknown required answers pause the workflow. Confirming an answer resumes it; correcting an answer supersedes its previous fact, invalidates approval, and survives a restart through the question's `needs_review` flag.

Required custom qualifications are added to the assessment as unconfirmed central requirements. A durable `form_fit` job sends the posting, form requirements, and relevant confirmed answers to the configured fit-assessment model. The same score gates apply. A high total cannot hide an unconfirmed required qualification. A qualifying result resumes preparation using the existing document versions; a nonqualifying result remains visible for review. Contact details are excluded from the model packet.

## Browser boundary

The application page shows six stages: check the role, prepare documents, prepare answers, review and approve, send, and confirm receipt. Its next-step panel separates what the agent has done, what the user needs to do, and what follows. Completed evidence and past activity remain available under expandable sections.

For a Greenhouse application stopped by the previous demographic or adapter limitation, **Refresh form and prepare answers** reads the current form and reuses confirmed answers. **Open browser and fill application** stages a supported form for review. An existing submission attempt blocks this path. For other manual handoffs with no submission attempt, the next action is **Review answers and files**. **Mark package reviewed and continue** records a durable review of the exact answers and selected file hashes through `POST /api/applications/{id}/handoff-review`. It does not create submission approval, an attempt, or a receipt. The journey leaves Review & approve incomplete until an actual submission approval exists. The API rejects pending answers, missing resumes, changed evidence, paused or imported records, and existing submission attempts. Changes to reviewed content require a new review. Answers remain editable during a manual handoff.

After review, **Open employer application** becomes the primary action. The user transfers the package, completes any additional employer questions or consents, and reviews the final submission page in that browser. **Already submitted? Record the confirmation** reveals receipt entry. An unresolved recorded attempt instead opens receipt recovery immediately and blocks the package-review path. Supported automated applications keep the existing per-application approval and receipt controls.

The Lever worker handles the standard single-page form: text fields, textareas, native selects, radio groups, checkbox groups, and one PDF resume. Its executor has been tested against a local representative portal. Public Lever and Greenhouse forms have been inspected read-only. No live employer application has been sent to validate the executor.

For Lever, the UI shows a local answer plan before approval. After matching approval, the worker opens an isolated visible browser, checks the current form against the reviewed contract, and records a durable attempt before typing or attaching. This earlier checkpoint accounts for portals that upload or save as soon as a field changes.

The local API token is never installed on an employer context. Cross-origin requests, sockets, automatic resume parsing, and unreviewed POSTs are blocked. Once personal data enters the page, even GET requests are blocked except the expected receipt navigation. The final request must match the reviewed field values and attachment names. Chromium omits file contents from intercepted POST data, so the worker supplies the approved local bytes, verifies their hashes, and validates the reconstructed multipart request before forwarding it. Only one matching POST is permitted.

The reviewed form's normal submit control initiates the request. The worker does not use an employer API key, bypass CAPTCHA, or treat a click as receipt. Receipt requires the expected requisition-specific confirmation route, a recognized confirmation heading, and a captured screenshot. Missing confirmation leaves the application unresolved. An existing attempt blocks a new submission after a restart, timeout, or cancellation. Reconciliation never clicks Submit.

A material form edit invalidates approval before candidate data is entered. Official verification must also be less than 24 hours old, matching the scoring policy. A challenge encountered before an attempt pauses the application and saves a normal-browser handoff. CAPTCHA and login portals currently need that handoff. The executor deliberately rejects unrecognized widgets, additional attachments, changed final controls, and unsupported receipt routes.

## Greenhouse browser adapter

`greenhouse_browser.py` handles text fields, narratives, native and React-select dropdowns, phone formatting, and PDF resume/cover-letter widgets. It verifies labels, choices, required controls, file bytes, and filled values. Supported self-identification surveys and demographic consent use the explicit choices described below. Unrecognized processing or retention terms, required education, location widgets, and unsupported custom uploads stop with a specific reason. Optional education is left blank.

**Open browser and fill application** refreshes the public question definitions, resolves answers through the existing memory/evidence service, and applies fit gates. It then opens an isolated visible browser. Public page assets load before candidate information is entered. All subsequent outbound requests are blocked, including email validation, autosave, analytics, and final submission. The browser displays a local-review banner.

Greenhouse normally uploads a file as soon as it is selected. During local review, the adapter supplies temporary upload metadata and answers that upload request inside Playwright. The file widget displays the selected filename, but no employer upload occurs. A staging-only upload-progress event lets the native widget finish its local display; it does not simulate submission or employer receipt. File hashes and a private screenshot document this review. The app records no attempt or attached/submitted artifact at this stage.

Prepared documents without matching employer upload fields remain available but are removed from the attachment selection. The final review explains each omission. For example, an employer form may accept a resume and narrative answers without offering a cover-letter upload.

An approved sending run opens a fresh browser, rechecks the form, and records the durable attempt before the first actual file upload. `greenhouse_transport.py` validates storage policy fields, filename, selected artifact ownership, and file hashes before forwarding an upload. It then checks the native JSON application request against the reviewed answers, current option IDs, confirmed upload URLs, and consent choices. Extra answers, files, or consents block the request. One initial application POST is allowed. A recognized email challenge can permit the bounded continuation described below.

The employer's native verification mechanism remains in place. A visible challenge pauses for user action; codes and tokens are not persisted. Receipt requires the matching confirmation URL, successful application and confirmation responses, a recognized heading, and a screenshot. Failure after the attempt checkpoint leaves an unresolved outcome. Restarting cannot blindly repeat an upload or submission.

The current upload destination allowlist covers Greenhouse's inspected US storage host. Other regions and custom storage configurations need validation before use. The request and receipt executor is exercised against synthetic fixtures; no real application has been sent to validate production acceptance.

### Email verification

Greenhouse can request an emailed code when its invisible reCAPTCHA requires additional verification. This is documented in [Greenhouse's spam protection guide](https://support.greenhouse.io/hc/en-us/articles/115005448066-Invisible-reCAPTCHA). The native form uses eight `security-input-*` controls. The adapter recognizes those controls and HTTP 428 responses, then pauses for employer verification rather than reporting an ordinary submission failure.

For recognized `captcha-failed` responses with an email recipient, or `invalid-security-code`, the user enters the code directly in the employer window and chooses **Continue verification** in the app. Pasting is handled by the employer page; typing one character per box also works. The worker uses the original browser, uploaded files, attempt, and approval. Before releasing a continuation it checks the approved answers, attachment hashes and URLs, native request token, pause/cancellation status, and a limit of three verification sends. It never supplies or solves a CAPTCHA.

Codes and native tokens remain ephemeral. API requests and queued jobs contain only the application ID. The response handler uses Playwright's [JSON response API](https://playwright.dev/python/docs/api/class-response#response-json) and saves only fixed challenge categories and HTTP statuses. Incorrect codes remain waiting; expired codes and unknown responses require employer instructions. A code email is not a receipt.

Closing the browser or restarting its worker loses the native verification session. Continuation then fails without opening another form, uploading files, or releasing a request. An interrupted continuation is never retried automatically. Upgrading an already running worker cannot add these controls to an existing browser session.

When an initial run ended with a recorded HTTP 428 and no later verification continuation, an unresolved application's outcome panel offers **Not submitted** alongside receipt confirmation. The user must confirm that they did not complete verification or submit elsewhere. This records a scoped outcome statement and sends nothing. **Retry approved application** then becomes available. It preserves the original approval, revalidates the current application, archives the earlier run, and opens a new browser. A subsequent unknown outcome cannot reuse that confirmation. Cases without this evidence still require handoff and outcome reconciliation.

## Answer preparation and personal questions

Exact confirmed answers are reused first. For unanswered factual questions, `form_answers` receives the current career facts used by document preparation, applicable confirmed answers, and the official posting. If that packet is insufficient, a bounded retrieval pass adds up to three current workspace documents. Generated drafts and historical documents cannot establish claims. `form_answer_review` checks each proposed answer against the same evidence before a factual answer enters the local form plan. Model output does not create a confirmed career fact.

Before model evaluation, known profile labels such as **LinkedIn Profile** map directly to the confirmed profile used by resume rendering. This works for custom employer field names and optional fields. The mapping retains the original question identity and source facts, and rechecks them before approval. Contacts stay local; this lookup makes no model or retrieval call. Application-specific answers and pending corrections take precedence.

An explicitly confirmed `agent_employee_referral=false` fact means applications prepared through this app have no employee referral. Recognized yes/no referral questions receive No; recognized referrer-name fields receive Not applicable. This rule does not apply to imported historical applications, override a confirmed local answer, or establish which job board supplied a listing. Unrecognized wording and incompatible options remain unresolved rather than being guessed.

Prepared answers retain their source facts, document versions, and both inference run IDs. Reuse checks the exact field, reviewed value, current evidence, model settings, and instruction fingerprints. Changed evidence or instructions require preparation again. The existing worker supplies cancellation and progress reporting. Completed evaluations can be reused after a restart. Explicit corrections remain pending for the user rather than being overwritten by another generated answer.

Personal questions are a separate case. For example, "What interests you about this role, and what would you bring?" combines motivation with career fit. Experience can support the latter, but cannot establish the former. Without confirmed personal context, the planner flags human intervention and leaves the answer blank. It shows available career evidence separately. A generated cover letter is not evidence of personal interests. When confirmed personal context exists, a reviewed draft can be offered for the candidate to edit and confirm; it is never silently adopted as their perspective. Commitments, signatures, and ambiguous authorization questions also require applicable explicit answers.

The UI labels missing personal context and provides **Prepare answers from my records** to retry preparation. Model failures, conflicting facts, failed reviews, and unsupported claims remain unresolved. Offline fixtures exercise these controls without paid calls; they do not claim to perform semantic evaluation. Question classification uses explicit text patterns plus the model instructions, so unusual wording can still require review.

**Change answer** opens the correction editor, fills it with the prepared value, and moves keyboard focus to the input in view. Reopening an unsaved edit preserves its draft. **Confirm answer** saves the correction; later preparation retains that explicit answer instead of replacing it with the profile default.

## Deployment setting

If the guarded browser stops before the final application request, the app can offer **Retry approved application**. This action rechecks the existing approval and file versions without asking for approval again. It is available only when a completed run records that no final POST was released. An interrupted run without that evidence still needs receipt reconciliation. The failed job remains in the activity history.

Upload request comparisons account for Chromium adding `/` to a storage URL with an empty path. The original metadata stays unchanged because Greenhouse constructs the uploaded file URL by appending the key. Upload failures report the failed step; signed storage fields and verification tokens are not logged. The implementation follows Playwright's [request body](https://playwright.dev/python/docs/api/class-request#request-post-data-buffer) and [request continuation](https://playwright.dev/python/docs/api/class-route#route-continue) contracts.

Greenhouse's native submission can include an unfilled employment row even when no employment controls are shown. The adapter accepts only known fields with blank company, title, and dates, and `current: false`. Populated history, unknown fields, and additional consents remain blocked. This does not add career facts or relax checks on reviewed answers.

Deliberate network restrictions use Playwright's [`blockedbyclient` error](https://playwright.dev/python/docs/api/class-route#route-abort). Analytics, Quick Apply, and unapproved background data requests remain restricted. A blocked final request records a fixed reason code and a readable job error without saving request bodies or tokens. Greenhouse's own Content Security Policy and CAPTCHA are not changed. Browser console errors alone do not establish that the employer rejected an application; the transport records whether a final POST was released and whether a response arrived.

`jobsearch submissions --mode enabled` saves the deployment setting privately. Restart both services to apply it. New installs default to disabled; an explicit `JSA_LIVE_APPLICATIONS` value overrides the saved setting. Both the approval service and browser worker enforce this setting. Enabling sending does not authorize an application: the existing **Approve & send this application** button grants approval for the reviewed payload and queues its sending run. No extra approval screen is required. Development tests use fixtures.

Greenhouse supports browser review and an approval-bound sender for the controls described above. Real uploads and sending require the enabled deployment and an exact matching final-review approval. Breezy, Workday, Ashby, and other unsupported portals still need browser adapters. There is no general-purpose agent that clicks through arbitrary pages. User takeover and employer receipt confirmation remain available when the automated route stops.

Migration 007 adds the persistent correction flag. Existing backup and restore commands cover it through the normal PostgreSQL dump. Form plans live in application payloads; browser profiles, captures, prepared files, receipts, and handoffs remain under private state. The original ODS remains authoritative for imported statuses and is not written by this workflow.

The implementation uses the existing pinned Playwright 1.64.0 and HTTPX 0.28.1 dependencies. The [Playwright network documentation](https://playwright.dev/python/docs/network), [input actions](https://playwright.dev/python/docs/input), [Lever public posting API](https://github.com/lever/postings-api), and [Greenhouse job board API](https://docs.greenhouse.io/job-board.html) were checked before adapting the integrations. The Greenhouse control and transport structure was also inspected on the public employer page using fictitious applicant values with outbound application traffic blocked.

## Saved self-identification answers

Greenhouse inspection requests both `questions=true` and `demographic_questions=true`. The parser retains standard EEOC questions, employer demographic surveys, displayed choices, option IDs, descriptions, and demographic-data consent. Supported controls include single and multiple selections, self-description text, and the conditional Hispanic/Latino and race controls. Unknown controls still stop for inspection.

The first encounter asks the user for an explicit choice, including leaving an optional question blank. **Global** saves that response for reuse; **This application only** limits it to the current role. Reuse matches normalized question wording, selection type, choices, and self-description capability. Employer field IDs and option order can differ. Different questions, such as protected-veteran classification and any military service, remain separate. Changed choices require confirmation again. The app never infers these answers from a resume or a model output.

Saved self-identification facts are excluded from inference packets for scoring, writing, and answer preparation. Their lookup does not call retrieval. Corrections supersede previous facts and invalidate dependent cached answers and approvals. Like other application records, the choices remain in private local storage and the reviewed application payload.

Consent to sending demographic responses applies only to the named employer application. If the user declines that consent while retaining survey answers, the app asks them to either consent or leave the optional survey blank. It does not select a decline-to-answer option or grant consent on their behalf. Other processing and retention consent variants still require a browser handoff until their displayed terms have an adapter.

The sending boundary compares the approved choices and self-description text against Greenhouse's native `demographic_answers`, EEOC option IDs, and `data_compliance` values. Extra answers, changed IDs, unapproved text, and additional consents block sending. Each sending run still requires the existing per-application approval and receipt check.

The integration follows the [Greenhouse Job Board API](https://docs.greenhouse.io/job-board) and [custom demographic question documentation](https://support.greenhouse.io/hc/en-us/articles/360004588971-Custom-demographic-questions). The native controls and serializer were checked on October 20, 2026. Public-form inspection checked controls without entering candidate data. Synthetic tests exercise saved answers, corrections, scope, privacy, browser filling, request validation, approval, and receipt capture.

A separate fit blocker can still stop sending after the survey is resolved. The journey names that step and links to fit review. An unattempted manual handoff can be rescored or have requirement decisions corrected; submission history prevents this recovery path. Package review never changes fit or grants submission authority.
